# Binding-Driven Execution Design

## Purpose

This document defines the design and invariants for future binding-driven
runtime execution. It is intentionally a design step only. Runtime behavior,
planner behavior, agent behavior, and action execution are not changed by this
document.

The target model is:

```text
shared capability
-> agent binding
-> local skills / resources / contracts / context
-> execution
```

This keeps Juniper's semantic authority in the shared runtime while allowing
agents to specialize how they use shared capabilities.

## Current State

Juniper now has canonical shared semantic registries under `agents/shared/`:

- `agents/shared/artifacts/artifacts.json`
- `agents/shared/capabilities/actions.json`
- `agents/shared/semantics/operations.json`
- `agents/shared/transforms/transforms.json`

Alexis has explicit capability bindings at
`agents/alexis/capabilities/bindings.json`. Those bindings are metadata only.
Current audits validate that each binding references an existing shared
capability and exact local skill/resource references.

The runtime does not yet consume agent capability bindings during planning,
context assembly, skill loading, or execution. Existing planner and execution
behavior remains authoritative until a later implementation phase wires binding
metadata into specific runtime boundaries.

## Binding Resolution API

The canonical read-only resolver lives in `runtime.bindings`:

```text
resolve_agent_binding(agent_name, shared_capability_id)
```

It returns either an `AgentBinding` or a `BindingResolutionError`. Normal
resolution misses are typed return values, not `None`, and not implicit
fallbacks. This makes missing bindings observable before they are wired into
execution.

`AgentBinding` contains the resolved agent name, binding ID, shared capability
ID, skill/resource references, tone, approval policy, manifest path, and raw
binding data. The raw data is included for audit/provenance visibility, not for
direct execution.

`BindingResolutionError` contains an error code, message, manifest path when
known, and details such as missing local skill/resource IDs. Current failure
codes include missing agents, missing manifests, missing bindings, unknown
shared capabilities, malformed bindings, missing local references, duplicate
bindings, invalid approval policies, and approval policy weakening.

Missing bindings must fail explicitly because silent fallback would create a
second, implicit routing system. Future runtime integration may define an
explicit fallback policy, but the resolver itself does not keyword-match,
alias-match, or switch to another capability.

## Binding Trace Observability

Binding trace observability is available before execution integration through:

```text
python tools/trace_agent_bindings.py <agent_name>
python tools/trace_agent_bindings.py <agent_name> <shared_capability>
```

The trace command resolves bindings through `runtime.bindings` and prints the
shared capability, binding ID, local skills, local resources, tone, approval
policy, manifest path, and validation status. Missing or invalid bindings are
reported with `BindingResolutionError` fields instead of being hidden.

This traceability exists before runtime consumption so future context-builder,
skill-selection, and execution-composition work can prove coverage without
changing planner or execution behavior. It also gives autogenerated agents a
read-only acceptance check: generated bindings can be traced and validated
before any generated agent is allowed to participate in runtime execution.

## Planned Capability Trace Observability

Planned capability trace observability is available through a read-only runtime
helper:

```text
trace_planned_capability(
    request_id=...,
    agent_name=...,
    shared_capability=...,
    semantic_operation=...,
    expected_output_type=...,
)
```

The helper returns a `PlannedCapabilityTrace` containing the request ID, agent,
shared capability, semantic operation, expected output type, resolved binding,
resolution status, typed resolution error when present, local skills,
resources, tone, and approval policy.

This layer exists before execution integration so the runtime can observe the
future composition chain without changing planner decisions, dispatch, skill
loading, or action execution. Future phases can consume this trace layer as a
stable contract: first for telemetry and audits, then for context enrichment,
then for skill selection, and only later for capability/action execution.

Autogenerated agents will use the same trace layer as an acceptance check. A
generated agent should be able to prove that each planned shared capability
resolves to a valid local binding before any generated binding participates in
runtime execution.

## Binding Trace Telemetry

Planned capability traces may be emitted as telemetry only when explicitly
enabled with:

```text
JUNIPER_TRACE_BINDINGS=1
```

The default is off. When enabled, read-only helpers serialize a
`planned_capability_trace` payload containing the request ID, agent, shared
capability, semantic operation, expected output type, resolution status, and
resolved local binding metadata. Failed binding resolution is reported as a
structured error payload and does not interrupt runtime execution.

This telemetry exists to observe future execution-composition behavior before
bindings participate in execution. It must not alter planner decisions,
dispatch, approval policy, skill loading, context construction, or action
execution.

## Planned Shared Capability Provenance

Execution planning carries an optional `shared_capability` field as
provenance. The planner sets this field only when semantic state already gives
it a confident capability identity, such as exact artifact creation mappings
from `email_draft` to `draft_email`, `lower_third` to `create_lower_third`, and
`producer_note` to `producer_note`. Workflow action capabilities, such as
`send_email`, require an explicit capability from the gate/planning path.

The runtime consumes this field passively for binding trace telemetry. It does
not infer capabilities from request text, reinterpret semantic operations,
change dispatch, load skills differently, or execute bindings. Ambiguous
requests, transforms, conversions, and unsupported artifact types leave
`shared_capability` as `null`.

## Context Composition Boundary

The first proposed runtime consumption boundary for bindings is context
composition, not execution dispatch. The detailed design lives in
`docs/binding_context_composition.md`. That design keeps context additions
additive, bounded, attributable, and observable while preserving planner,
approval, dispatch, and execution behavior.

## Target Execution Flow

The target flow is:

1. The gate/planner identifies the semantic operation, capability, artifact, or
   transform using canonical shared registries.
2. Runtime resolves the shared capability ID from canonical capability
   definitions.
3. Runtime resolves the current agent's binding for that shared capability.
4. The binding contributes local execution metadata:
   - skill hints
   - private resource references
   - tone
   - context policy
   - contract hints
   - execution hints
   - optional approval tightening
5. Context building and skill loading use the resolved binding metadata through
   explicit APIs.
6. Execution remains transport-agnostic. Telegram, CLI, local workers, and
   future interfaces should all consume the same resolved runtime plan.
7. Actions remain parsed, validated, and approved by runtime action systems.
   Model text never directly executes tools.

The execution planner must not reinterpret semantics already normalized by the
gate/planner. Binding resolution is a composition step over normalized semantic
state, not a second planner.

## Binding Invariants

- A binding never redefines shared capability identity.
- A binding may specialize local tone, context, skills, resources, contracts,
  and execution preferences for one agent.
- A binding must reference a valid shared capability ID.
- Local skills must exist in the agent skill manifest or skill files.
- Local resources/tools must exist under the agent directory.
- Private resources stay agent-local. A resource used only by Alexis, such as
  `guest_db`, must not be promoted to `agents/shared/` just because a shared
  capability can use it.
- Approval policy may only become stricter locally, never weaker.
- A binding cannot downgrade `requires_approval=true` from the shared
  capability.
- Missing bindings must fail loudly or follow an explicit fallback policy. They
  must not silently degrade into keyword routing or implicit behavior.
- Binding metadata must be read through runtime-owned loaders and validators,
  not interpreted ad hoc by agents or transports.

## Binding Manifest Data Model

A future binding manifest may use this shape:

```json
{
  "bindings": {
    "draft_email": {
      "shared_capability": "draft_email",
      "skills": ["structured_actions"],
      "resources": ["guest_db"],
      "artifacts": ["email_draft"],
      "contracts": ["outreach_email"],
      "tone": "newsroom",
      "context_policy": {
        "include_user_preferences": true,
        "include_recent_guest_context": true,
        "resource_scopes": ["booking"]
      },
      "approval_policy": "shared_capability_required",
      "execution_hints": {
        "preferred_engine": "local_agent",
        "fallback_engines": ["cloud_fast"]
      }
    }
  }
}
```

Proposed fields:

- `shared_capability`: Required shared capability ID.
- `skills`: Agent-local skill IDs to load or prefer.
- `resources`: Agent-local tools/data sources used by the binding.
- `artifacts`: Artifact types the binding may produce or consume.
- `contracts`: Agent-local or shared contract hints relevant to the binding.
- `tone`: Local voice/style label.
- `context_policy`: Structured context assembly policy for this binding.
- `approval_policy`: Local approval tightening label. It cannot weaken shared
  approval requirements.
- `execution_hints`: Non-semantic execution preferences. These must not change
  capability identity or planner semantics.

These fields are declarative. They are not executable code and do not authorize
direct tool invocation from model output.

## Runtime Integration Phases

### Phase 1: Read-Only Validation And Provenance

Status: complete.

Current tools validate shared capability IDs and exact local skill/resource
references. Provenance reports binding status without changing runtime
execution.

### Phase 2: Context Builder Reads Binding Metadata

The context builder may receive a resolved shared capability and agent binding
from an explicit runtime API. It may use binding metadata to select bounded
context sources, such as Alexis booking context for `draft_email`.

This phase must not alter planner classification, transform semantics, or
approval behavior.

### Phase 3: Skill Selection Uses Binding Metadata

Skill loading may use binding `skills` as additive or priority hints after the
planner has selected operation and expected output type. Skill selection must
remain operation-aware. Artifact transforms must not receive action-envelope
skills unless the plan expects an action.

### Phase 4: Action/Capability Execution Uses Binding Metadata

Action parsing and capability validation may resolve the binding for the
current agent and capability before queueing or executing an action. Approval
requirements must be computed from the shared capability plus local
tightening.

This phase may connect resources only through explicit, validated runtime
adapters.

### Phase 5: Autogenerated Agent Manifests

Autogenerated agents can be assembled by selecting shared capabilities and
generating local bindings/resources/contracts. Generated manifests must pass
the same validation as handwritten agent bindings before runtime use.

## Safety And Approval Rules

- `send_email` remains distinct from `draft_email`.
- `draft_email` creates an email draft artifact or candidate content. It does
  not send.
- `send_email` queues or performs a delivery workflow and requires approval.
- A local binding cannot downgrade a shared capability's `requires_approval`.
- Dangerous actions need explicit approval policy and runtime enforcement.
- Approval checks belong to runtime action/capability systems, not prompts.
- Model output may request or describe actions, but direct tool execution must
  flow through structured parsing, capability validation, and approval.
- If a binding is missing for a capability that requires one, runtime should
  return a clear binding error or use an explicitly configured fallback policy.

## Alexis Example

Alexis currently binds four shared capabilities:

- `draft_email`
  - Shared meaning: create an email draft.
  - Local binding: newsroom tone, `structured_actions` skill, `guest_db`
    resource.
  - Future use: context builder may include bounded guest context and user
    outreach preferences.

- `send_email`
  - Shared meaning: queue an email delivery request for approval.
  - Local binding: newsroom tone, `structured_actions` skill,
    `approval_policy=shared_capability_required`.
  - Future use: action execution validates approval and never sends directly
    from model text.

- `create_lower_third`
  - Shared meaning: create a lower-third/chyron artifact.
  - Local binding: broadcast tone, `lower_third` skill.
  - Future use: skill selection can load lower-third instructions without
    redefining the shared capability.

- `producer_note`
  - Shared meaning: create an internal newsroom note.
  - Local binding: newsroom tone, `producer_note` skill.
  - Future use: context and contract hints can stay local to Alexis.

## Yossi Future Example

Yossi should not require copied global config or custom Python as the first
step. A future `agents/yossi/capabilities/bindings.json` could bind shared
capabilities such as:

```json
{
  "bindings": {
    "draft_email": {
      "shared_capability": "draft_email",
      "skills": ["yossi_outreach"],
      "resources": ["contact_notes"],
      "tone": "warm_practical",
      "context_policy": {
        "include_user_preferences": true,
        "resource_scopes": ["contacts"]
      }
    },
    "producer_note": {
      "shared_capability": "producer_note",
      "skills": ["yossi_summary"],
      "resources": [],
      "tone": "concise"
    }
  }
}
```

This would compose Yossi from shared capabilities plus local bindings,
resources, skills, and context policies. Any custom Python should be introduced
only when a real local resource adapter is needed and after manifest validation
passes.

## Non-Goals

- No keyword routing.
- No immediate runtime rewrite.
- No planner behavior change.
- No agent behavior change.
- No agent cloning.
- No creation of Yossi in this step.
- No direct tool execution from model text.
- No weakening approvals.
- No copying obsolete compatibility fields into canonical registries.

## First Implementation Step

The safest first implementation step after this design is a read-only binding
resolution API:

```text
resolve_agent_binding(agent_name, shared_capability_id)
```

It should return validated binding metadata or a typed missing-binding error.
It should not be called by execution paths yet. Initial use should be limited
to an audit or trace command that proves the API resolves Alexis bindings and
reports missing bindings deterministically.
